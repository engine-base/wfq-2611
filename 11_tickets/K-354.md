## 目的

PC（Bridge）の実行器が、いま動いている仕事のためにだけ、預けたログイン情報を 1 件取り出す契約の口 `resolveCredential`（POST /api/v1/bridge/credentials/resolve・device）を作る（今は 501）。D-128.57 の 4 つの守りのうち、口の側で持つ ②④ と ① を入れる：

1. 取り出しを頼めるのは、つないだ PC の常駐アプリ（PC の印）で、その PC が取った動いている仕事（running・asking）のためだけ（④・D-102.2）
2. 個人の物は持ち主の分身の仕事だけ。ワークスペースの物はそのワークスペースの人の仕事だけ（①）
3. 入れる場所（宛先のドメイン）が、その情報の「使える場所」の中のときだけ。外なら止めて持ち主に知らせる（②）
4. 答えは平文を返さない形：PC がその回だけの鍵の組を作って公開の鍵を送り、口はそれでしか開けない封で返す（関門 C8 の外に平文が出ない。ログ・中継・AI の道に乗っても読めない）

あわせて Bridge の取り出し（apps/bridge/src/vault.ts）と、確かめの道（login-check.ts・two-factor.ts・loop.ts）を、前の道すじ（/api/auth-ext/bridge/credentials/resolve・/bridge/credentials/check-result・/bridge/ask・/bridge/code）から契約の口（この口と K-355 の reportCredentialCheck）へつなぎ替える。前の道すじの口そのものは K-358 が消す。

- 使える場所の合わせ方（口と Bridge で同じ 1 つの関数・代表の答え answer=449e72553c59）：名前の取り出しは K-352 の `apps/api/src/features/F3/credentials/host.ts` の `hostnameOf`。中身は K-352 がレビューの指摘で直した後の版（枝 t/K-352 の 7787a4b3・2026-11-20）のまま：
  - `hostnameOf(v)`：前後の空白を落とすだけ（`v.trim()`）。**URL を読む前に字を変えない（NFKC をかけない）**。全角の区切り ／ ＃ ？ ＼ を半角に直してから読むと、ブラウザが読む行き先と違う名前になる（例 `https://example.com／@evil.test/` の行き先は evil.test なのに、先に NFKC をかけると example.com と読んでしまう）。空・空白を含む → null。`^[a-z][a-z0-9+.-]*://`（大小を問わない）で始まらなければ頭に `https://` を付けて `new URL`（投げたら null）。http・https でなければ null。答えは `url.hostname` を小文字にして末尾の点を 1 つ落とした物（空なら null）。全角の英字と点・日本語の名前は `new URL` が自分で半角・punycode に直す。URL の @ の前（userinfo）・道・問い合わせ・断片・ポートは名前に入らない
  - `destinationOf(v)`：前後の空白を落とし、頭が `*.` なら外して `hostnameOf` にかけ、付け直す（ここも NFKC をかけない）
  - `hostAllowed(target, destinations)`：`hostnameOf(target)` が null なら false。使える場所が `名前` なら同じかその下の階層（`.名前` で終わる）、`*.名前` なら下の名前だけ（名前そのものは当たらない）。使える場所が空なら通らない
  - 口は host.ts を import し、Bridge は区切りの中を 1 字も変えずに写した `apps/bridge/src/host.ts` を使う（Bridge は CommonJS・rootDir src で packages も apps/api も読めない。前例は packages/db/src/id.ts と apps/bridge/src/pairing.ts の同じ字・K144-SHAPE-019。2 つが同じことは K354-BRG-010 が見る）。名前は 1〜253 文字（名前に読めない・253 字超は 422 でなく 403 E-CRED-016）
- **口は、宛先（destination）だけ、入口が字をそろえる前の値で名前を取り出す**（2026-11-20 切る段の決め）：契約の口の入口（`apps/api/src/contract/op.ts` の `normalize`）は、体の文字を全部 NFKC と前後の空白落としにしてから口へ渡す。だから口が `a.input.destination` をそのまま host.ts にかけると、host.ts から NFKC を外しても、`https://hacchu-navi.example／@evil.test/` は入口で `https://hacchu-navi.example/@evil.test/` になり、使える場所 hacchu-navi.example に当たってしまう（K-352 の直しだけでは、契約の口を通る宛先には効かない）。口は体をもう一度読んで（`a.c.req.json()`・前例は `apps/api/src/features/F5/delegate/bridge.ts` の `rawBody` と `apps/api/src/features/F2/invitations/accept.ts` のパスワード）、そこの `destination`（文字であることは入口の契約の形が確かめ済み）を `hostnameOf`・`hostAllowed` にかける。ほかの欄（job_id・credential_id・executor_key）は今までどおり入口がそろえた値を使う。もう一度読めない・読んだ `destination` が文字でない（前例の rawBody の `.catch(() => ({}))` の形で `{}` になった回など）ときは 403 E-CRED-016（名前に読めない宛先と同じ・use_count 0・取り出さない・知らせも証跡の wrong_destination も書かない。`String(undefined)` を名前にかけない）
- 口と Bridge の判定は、同じ 1 つの表で試す（2026-11-20）：`apps/api/test/features/F3/credential-host-cases.json`（宛先 30 件：通る 9・使える場所の外 16・名前として読めない 5。全角の区切り ／ ＃ ？ ＼ と小さい形 ﹖ ﹟ ﹨ を @ の前に置いた宛先を含む）。口の試験（K354-API-005・010・013）は口を通して、Bridge の試験（K354-BRG-005）は `hostAllowed` を直に、同じファイルを字として読んで試す。host.ts の字が同じこと（K354-BRG-010）だけでは、口の入口の正規化のように host.ts の外でずれる穴を見つけられないので、振る舞いも同じ入力で両方を見る

## リスクと懸念

- レビュー Q の参考（指摘でない）：封の外の欄（destinations・kind・two_factor）は封の AAD に入っていない。中継で書き換えられても Bridge は気づけず、入れる直前の確かめはその destinations を信じる（TLS の内側の話・チケットが封の形をこう決めた）。直すなら封の形を決め直す事柄（PM に知らせる）
- 代表に確かめる（まとめ役が PM に出す）：使える場所が全部 `*.` で始まる物のログインの確かめをどうするか。今は仮の形（K-355 が確かめの仕事を積まず、行に理由を持つ。この葉は変えない）。「`*.` を外した名前を開いて確かめる」と決まれば、変わるのは K-355 の開く先と、この口の合わせ方（確かめの仕事のときだけ名前そのものを通すか）と K354-API-010 の後半
- 古い Bridge は K-358 の後に取り出せなくなる（前の道すじが 404）。確かめは止まった扱いになり、行に「Bridge が途中で止まった」と出る。自動の更新（update.ts）で新しい版に替わる
