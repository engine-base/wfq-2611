## 目的

チケットの本文を「自由な 1 枚の文書」として持つ置き場を DB に作る（決定 D-150.35・D-150.50）。区画ごとの入力欄はやめ、`ticket_sections` に鍵 `body` の 1 行（列 `body` ＝ `{ doc, text }`・版は `ticket_section_versions`）で持つ。種別を選んだときに入るひな形は `ticket_kinds.body_template`。作る関数 `app.ticket_create` に「本文 1 枚の道」を足す。

あわせて、本文の中身の形（文書の木 `doc`）と「doc → text」の関数を、口（K-432・K-437）と画面（K-567・K-568）が同じ物を使えるよう `packages/contracts` に置く。DB は text を作らない（口が作って渡す）。

**前の道は壊さない**：入力に `sections` が来たら今までどおり区画の行を書く。作る口 K-437・読む口 K-560・F5 の K-565・K-566 が入るまで、前の作る面・「AI に任せる」・完了が壊れないようにするため。前の道を消すのは最後の葉 K-578（今ある区画の中身を本文に移すのは K-575。K-578 が区画の入力を受けるのをやめ・`kind_sections` に凍結の印を付ける）。`kind_sections` はこの葉では触らない。

## 前提と制約

分類: CRUD

- 関門は C2（DB）。口は作らない（`apis: []`・`canvas: []`）。読む口 `getTicket` の答えに本文を載せるのは K-560、書く口は K-432・K-437
- **text は口が doc から作って渡す**（DB の関数に doc → text を書かない）。理由：SQL にも同じ変換を書くと、2 つの実装が少しずつずれる（L-002 と同じ形）。DB が守るのは、形（doc は type が doc で content が配列・text は文字）と上限だけ。口の入口の確かめ `validateDoc` と同じ数にする（下の「受け持ちをまたぐ名前」）。画面から text は受けない（口が `docToText` で作る・K-432・K-437 の仕事）
- 上限（DB の `app.ticket_body_valid` と `packages/contracts/src/doc.ts` の `DOC_MAX_*` が同じ数）：doc の長さ 1,048,576 バイト・text 1,048,576 バイト・入れ子 12（入れ子は口の入口だけで見る。DB は大きさで頭打ち）。リンクは http・https・mailto だけ・長さ 2,048
- **文書の木の形**（ProseMirror の JSON と同じ並び）：節は 段落・見出し（level 2 か 3）・箇条書き（bulletList・listItem）・チェックの箱の並び（taskList・taskItem の `attrs.checked`）・表（table・tableRow・tableHeader・tableCell）・引用・コード・画像の置き場（`attrs.caption`・`attrs.attachment_id`＝今は null）・改行。印は 太字・斜体・文字の色（red・teal・amber）・線で強調（highlight・下絵の `<mark>`）・リンク。**薄い字の説明（ひな形の説明）は `attrs.ghost: true`**（書き始めると消える。素の文字には入れない）。「/」「#」「@」「注意の枠」は作らない（D-150.48）。画像は押せない形（D-150.57）
- 種別のひな形は、既定の 4 種別（タスク・課題・QA・会議）に同じ物を入れる（下絵 `apps/web/features/F4/doc/views.tsx` の `Template`：目的・完了の条件・実施事項・前提と制約・参考の見出しと薄い字の説明）。会社が種別ごとに直す画面は段 10。会社が直した物は、入れ直す関数が上書きしない
- 新しい会社の種まき：`app.ticket_basics`（0071）は作り直さず、`tenants` の引き金 `tenants_ticket_body_template` で入れる（引き金は名前の順に走るので `tenants_ticket_basics` の後。K561-DB-001 が会社を作った直後に入っていることを見る）。理由：`ticket_basics` の 80 行を丸ごと写すと、後の葉がそこを直したときにぶつかる
- migration の名前：番号の下 2 桁の決め（`2026112209NN00`）だと K-561 は `20261122096100` になるが、分が 61 で時刻の形（`isTimeName`・分は 59 まで）を通らない。そこで **`20261122090100_ticket_body.sql`**（09:01:00）にした。K-561 → K-437（093700）→ K-438（093800）の順は名前の順で守れる（K-432〜K-435 の 0932〜0935 より前）。同じ形の問題は K-563（63）にもある（まとめ役に頼むこと）
- `app.ticket_create` は 0090 の作り直し（`create or replace`）。入力の鍵・答えの形・断りの code は前のまま（`FORBIDDEN`・`KIND_GONE`・`ASSIGNEE_GONE`・`PARENT_NOT_FOUND`・`PARENT_DEPTH`・`NOTIFY_GONE`・`SECTION_REQUIRED`）。足すのは入力 `body` と断りの code `BODY_INVALID`（422・field `body`）だけ。口が先に形を確かめるので、`BODY_INVALID` に届くのは口をすり抜けた物だけ（最後の砦）
- 入力に `body` が在れば：必須の区画の確かめ（`kind_sections.mode = required`）はしない（D-150.49：必須の区画は無い）。`body` と `sections` が両方来たら `body` だけを書く（区画の行は書かない）。`body` に `doc`・`text` 以外の鍵が在れば捨てる
- 本文が空（節 0 個・text 空）でも作れる。`body` が無く `sections` も無ければ、前のとおり必須の区画で断る（K-437 が入って口が `sections` を送らなくなるまで）
- 別の会社・書けない人：前のとおり 403 `FORBIDDEN`（グループの確かめ）で、何も書かない。本文の行は作ったチケットの子の行で、読める人は前のとおりチケットに従う（RLS・`app.ticket_child_same_tenant`）
- **本文の道具の決め（代表 2026-11-22・出来合いの部品の機能を絞らずに使う）は、この葉に当たらない**：この葉が決める文書の木（節と印・色は red・teal・amber）は変えない。足す節と印（番号つきの並び・区切りの線・見出しの段 4・寄せ・セルの結合・下線・取り消し線・行の中のコード・上付き・下付き・`#rrggbb` の色）は、この葉の後に切る別の葉（文書の木に足す節と印の葉。番号は切ったときに範囲の文書 `07_functional/段5-F4/切り方.md` に書く）が `validateDoc`・`docToText` を広げて受ける（この葉で通る文書は、その葉の後も全部そのまま通る）。この葉の行・試験・表は変えない

## リスクと懸念

- 節の数の上限は持たない（つなぎで決まった：木全体の数は契約の言葉で書けず、検査の例外も足さないため。守りは入口の体の大きさ 1MB と、契約に書ける深さ 12・形だけ）。DB の `app.ticket_body_valid` も節を数えない
- 前の道（`sections`）は K-578 まで残る。`body` と `sections` が両方来たら、K-437 の口は `body` だけを DB へ渡し（`sections` は捨てる）、DB も `body` を優先する
- 大きさの境目：DB の `app.ticket_body_valid` は `jsonb::text` の長さ、口の `validateDoc` は JS で数えた長さで見る。jsonb が整形で空白を入れるぶん、境目（`DOC_MAX_BYTES`）のごく近くでは数がずれ、口が通した木を DB が断る（422・`BODY_INVALID`）ことがありうる。K561-DB-013・DOC-006 は境目から遠い値で見る。ずれは断る側（DB）に倒れるので、通さない向きの誤りで、書けてしまう向きの誤りは無い（最後の砦の口が 422・欄 body に直す）
