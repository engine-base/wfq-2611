## 目的

spec-sync の L は `layer_audit.py --run` で、層ごとの check を実際に流す。その中の `packages/db/migrations/*.sql` の層（D-145・D-133.6 の db: true）は `pnpm exec vitest run packages/db/test` を流す。PM の実行では **29 件が赤**（32 秒）だった。原因を調べた（実測）：

1. この Mac の `kaname_test`（`127.0.0.1:55433`）は、`app.schema_migrations` が `0075_workspace_people.sql` で止まった**古い残り物**（tenants 2 行・migration が 128 本ある今の木に追いついていない）。vitest は DATABASE_URL が無いとここにつなぐ。
2. 残り物の上で今の migration を当てると、`0076_clone_ops.sql` の `insert into operations … app.ops_tenant_id()` が `operations_tenant_id_fkey` で落ちる → 18 のファイルが起動で落ちて 29 件が赤。
3. **使い捨ての新しい DB（`kaname_tmp_pmsync`）で同じ vitest を流すと、181 本のうち 180 が緑**（実測：169 秒）。残る 1 本（`repository.test.ts`「init は表が無いと落ちる」）は、`URL.replace(/\/kaname_test$/, "/postgres")` が **DB の名前が `kaname_test` のときだけ**管理 DB に替わる書き方で、別の名前だと同じ DB のまま「表が在る」になり赤になる。これは試験の誤り（名前の決め打ち）。

判断：

| 赤 | 判断 |
|---|---|
| 29 件（古い kaname_test） | **検査の設定の抜け**：製品の食い違いではなく、手元の DB が古い。CI は毎回まっさらな DB なので出ない。手元の `kaname_test` を作り直す（Docker に触る・本人の DB を壊す）のではなく、**層の検査が自分で使い捨ての DB を作って捨てる**ようにする（memory の「DATABASE_URL_ADMIN=…/kaname_tmp_<番号>（使い捨て）」と同じ運用を道具にする） |
| 1 件（repository.test.ts） | **本当の食い違い（試験の誤り）**：名前を決め打ちしない書き方に直す（`/\/[^/?]+$/`）。carry: で切る段が直した版を運ぶ |

検査は緩めない：vitest は今のまま全部流す（`packages/db/test` 全部）。DB を黙って切り替えるのではなく、DATABASE_URL が env に在れば（CI）そのまま使い、無いときだけ使い捨てを作る。
