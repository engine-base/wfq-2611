## 目的

詳細の項目の表の「確認項目」の行（画面は K-450）が開いたとき・項目を足したときに呼ぶ契約の口 2 本を作る（今はどちらも 501）：
`listTestSpecs`（GET /api/v1/tickets/:id/test-specs）と `createTestSpec`（POST /api/v1/tickets/:id/test-specs）。あわせて、確認項目の表の形を新しい形（D-150.39）に直す。

- 確認項目の行は **文（title）とチェックだけ**（D-150.39）。種類（機械・AI・人）・判定の型・設定値は足すときに決めない・口の入力にも答えにも出ない（列 `check_kind`・`judge_type`・`params`・`off_reason` は表に残るが使わない）
- 足す入力は `title` だけ。前後の空白を落として 1〜200 字（D-150.28）。足したときはチェック無し・出どころ `manual`（人が口から足した）
- **足したら、同じ取引でやり取りに 1 行**（`ticket_messages` の kind `change`・「〈名前〉が確認項目を足しました：〈文〉」。D-150.40・D-128.45）。人が足したので `author_member_id`＝その人。記録の表は別に作らない
- 完了した・消されたチケットの扱い：読むのは完了後も 200（`meta.can_edit` が false）・足すのは完了後 409・E-SPEC-001（D-150.33・D-150.56）・消されたチケットは読むも足すも 404
- 画面が出し分ける物は口の答えで決める：`meta.can_edit`（書けて、完了していない）

**表の形（この葉が作る。後の葉が使う名前は「受け持ちをまたぐ名前」の表）**：
`test_specs` に ① `check_kind` を任意に（not null を外す）② `checked_at`・`checked_by_member_id`・`checked_by_ai`（チェックの印と付けた人。付けるのは K-435）③ `source`（`manual`・`knowledge`・`ai` の 3 つ・既定 `manual`）と `source_ref_id`（uuid・任意・出どころのページなど）。`tickets` に `no_spec_reason`（text・任意。K-565 が「AI に任せる」の 0 件のとき使う）。
**`source` と `source_ref_id` はこの葉では列と既定だけ**（ナレッジの「必ず守る」のページから入れる仕組みは段 10 か AI の段が作る）。`createTestSpec` の入力では受けない。`listTestSpecs` の答えには `source` を入れる（`source_ref_id` は答えに出さない）。

直す（文・チェックの付け外し）・外すは K-435、作るとき `specs[]` から足すは K-437、使わない理由を書くのは K-565、画面は K-450。

## 前提と制約

分類: CRUD, LIST, PERM

- **口は 2 本とも新しい専用の入力・答え**（表の写しは使わない）。足す入力は `title` の 1 欄だけ（strict）。**`ticket_id` は道（:id）から決め、体に入れさせない**。`check_kind`・`judge_type`・`params`・`source`・`source_ref_id`・チェックの列・version・off_reason・id・tenant_id・deleted_at も体に入れさせない（知らない欄は 422）
- **断る番号**（控え帳：422＝契約に書ける形の誤りだけ／404＝無い・見えない／409＝今の状態ではできない／検査の例外は足さない）：題名の形の誤りは番号なしの **422・VALIDATION_ERROR**（欄は `title`）／見えない・無い・消された・別の会社は **404**・NOT_FOUND／書けない人は入口の **403**／完了したチケットは **409・E-SPEC-001**（置き場は `errors.d/K-434.json`・E-SPEC-001〜019 の枠。K-435 の分は 020〜）
- **404・409 の答えの体は `{ error, code }` だけ**（控え帳 2026-11-21 01:15 K-385・2026-11-20 20:50 K-401：`field`・`details`・`detail` を付けない＝在るかを漏らさない・欄を指さない）。入口の 404（見えない・別の会社・無い uuid）も同じ形。422 だけが `details` を持つ
- **404 の出どころ**：見えない人・別の会社・無い uuid の 404 は、入口（`op.ts` の行の確かめ）が先に `{error:"not_found",code:"NOT_FOUND"}` で返す。この葉の口が返す 404 は、入口では見える物（消されたチケット）だけ（口の文でも同じ答えにする・二重の守り）
- **422 は全部、契約に書く**（`VALUE_RANGES` の `title`：空白だけでない・1〜200 字。`INPUT_RULES` は使わない・`UNEXPRESSIBLE_422` は空）。入口の zod は値域の言葉を読まないので、**題名の確かめは DB の関数 `app.test_spec_title_check` が 1 か所で持つ**（口は体の `title` を渡して、外れた答えを欄 `title` の 422 にするだけ。契約の値域は関数が受ける集合より狭く書かない。契約と関数の 2 か所が同じ決まりを言うので K434-API-009 が食い違いを拾う）。体が文字でない（数・null・配列）も同じ関数が断る
- 題名は前後の空白（全角の空白・タブ・改行を含む）を落として保存する。長さは落とす前の生の字で数える（200 字を超えれば 422）。落とした後が空なら 422
- **上限は置かない**（前の版と同じ・D-130.1。1 チケットの項目数に上限は無い）。一覧は全部を作った順に返し、cursor・limit は入口の共通の形の確かめだけ。**500 行で切る**（501 行目があれば捨てて、ログに `[test-spec] 一覧を 500 行で切った` を 1 行・題名は出さない）。並べ替え・絞り込みは受けない
- 完了した（`tickets.completed_at` が入っているか段が `done`）チケットは足せない（**D-150.33・D-150.56**：確認の結果が項目を指すので、完了後に足す・外す・付け外しすると結果の根拠が変わる。読むのは完了後もできる）。確定の瞬間と足すが同時に来たら、**チケットの行のロック（足すは `for share`・完了の確定 `app.ticket_complete` は `for update`）で順番にし**、完了の後に来た方は 409
- チェックの付け外しは K-435。**文の直しの決まり（D-150.55）**：チェックが付いていない間は直せる。付いた後は、外してから直す（直す口は K-435 が持つ。この葉は題名の確かめ `app.test_spec_title_check` を K-435 と K-437 が同じに使えるよう置く）
- 外へ出ない：メールも知らせ（受け箱の行・関門 C6）も出さない（項目を足しても誰にも知らせない。やり取りの 1 行は流れに載るだけ）。AI も PC も呼ばない
- ログに題名の文を出さない（チケットの id と例外の種類だけ）
- 業務の型は無くした（D-150.60・本線に残る分は K-582 が外す）。この葉は依存に持たない
