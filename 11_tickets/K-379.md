## 目的

預けたログイン情報の通しの道（画面 → 本物の口 → 本物の Bridge の輪 → 本物の Chrome → 的のログイン画面）を確かめる画面の試験は、今の CI のどの段も流していない。CI の画面の組（web）が流すのは G48（e2e:k の一覧）・G59（中間テスト）・G70（見た目の突き合わせ）だけで、Bridge の組み立て（apps/bridge/dist）も無い。だから段 4 の K-370 の通しの 8 行は「手元で流して記録を残す」仮の形（人が確かめる行）になっていた。

2026-11-19 のお試し（使い捨ての枝 tf-trial/bridge-chrome・run 44513671610・44514676916）で、**CI の VM の中で Bridge の輪が Chrome を動かせる**と分かった：画面の組の準備の後に `pnpm --filter @kaname/bridge build`（1〜2 秒）を足すだけで、VM の像の Chrome（google-chrome-stable）を Bridge が頭なしで起こし、Bridge の仕事 5 件が全部閉じた。env は画面の組の今のままで足り、xvfb も Electron の本体も要らない。

PM の決め（2026-11-19）：**画面の組に専用の段を 1 つ足す小さな葉を先に切る**。この葉がそれ。

- 画面の組の「画面を立ち上げる」の後に、① Bridge を組み立てる段 ② 専用の段 **G73**（`scripts/ci/web_run.py gate 73`・K-238 の G70 と同じ形・JUnit は別の名前 `junit/web-bridge.xml`）を足す
- **全部の CI では必ず流す**。**チケットの CI では、Bridge と預けたログイン情報の道を変えた葉だけ**（範囲の地図 `web_select.gates` の 73 の on に当たる変更・その段の試験を持つチケットと依存のチケット）
- この葉が入る時点では K-370 の通しの試験はまだ無い（K-370 は K-358 の後）。本線の今の `apps/web/tests/screens/qa-b-login-check.spec.ts` は、セッションの見張り（端末が変わると閉じる・K-20）とぶつかって落ちるので段の試験にできない。だからこの葉は、**段 4 のほかの葉で壊れない小さな見張りの試験を 1 本**持つ（`apps/web/tests/bridge/k379-bridge-chrome.spec.ts`・3 行）：組み立てた Bridge の、Chrome を起こすいちばん下の部品で頭なしの Chrome を起こし、的 `/dev/fake-login` を開いて読む・入れる・押す。Kaname の口（預ける道・仕事の道）は通さない
- K-370 は、この葉の後に、通しの 2 本をこの段の試験の一覧に足す（K-370 の「依存の理由」）

前からの通しの試験 `apps/e2e/journeys`（j01・j02）が CI で流れていない件は、この葉に入れない（PM が代表に聞く）。

## リスクと懸念

- **台の Chrome が無い・起こせないと、この段は赤になる**（飛ばさない）。VM の像を作り直すときは Chrome を入れる（ticket-flow.yaml の vm.warm に在る）。Chrome の `Default` の置き場の名前は Chrome の決まりで、Bridge（login-check.ts の noPasswordManager）も同じ名前を前提にしている
- **on は glob**：預けたログイン情報の migration は、名前に credential を含む物だけ当たる（段 4 の 4 本は当たる）。名前に入れない migration や、on に無い所から通しの道を壊す変更は、チケットの CI では見つからず、大分類の終わりの全部の CI で見つかる
- Bridge の src だけを変える葉でも画面の組が起きるようになる（今までは起きなかった）。画面の行を持たない Bridge だけの葉（K-354・K-359・K-366 など）は、チケットの CI の中で画面の組（準備・組み立て・G70・G73）が流れ、その分だけチケットの CI が長くなる
- **Bridge が組み立てられない変更（型の誤り）が本線に入ると、画面の組が起きる回はどの葉の回でも組み立ての段で赤になる**（G48・G59・G70 は続けて流れ、行の記録は出る）。static の組の型の検査は apps/bridge を含まないが、Bridge の src を変えた葉は画面の組が起きる（jobs.web.paths）ので、画面の行を持たない葉ならチケットの CI の中の組み立ての段で見つかる。画面の行を持つ葉（画面の組が後回し）だけ、見つかるのが取り込んだ後の画面の回になる。今までは staging の回まで見つからなかった物が早く見つかる側に倒した形。どの葉でもチケットの CI の中で見つけたいなら、static の組に Bridge の型の検査（`pnpm --filter @kaname/bridge type-check`）を足す葉が要る（この葉には入れない・まとめ役が決める）
- on と jobs.web.paths に Bridge の `package.json`・`tsconfig.json` を入れた（PM の決め 2026-11-19 夜）：Chrome を起こす部品（@playwright/mcp が持つ playwright-core）の版を上げる葉・組み立ての設定を変える葉は、その葉の CI で G73 が流れる。根の `pnpm-lock.yaml` を変える葉は、前からの決まり（画面の試験が全部に倒れる道）で G73 も全部流れる
